**Rules for this file**

- An item is added the moment work is blocked, skipped, or knowingly deferred — in the same change that discovered it.
- An item is removed only when it is genuinely done (and recorded in the relevant `DONE.md`), or explicitly dropped with a reason.
- "Needs you" items name exactly what to supply and which file/decision it unblocks.

Related: `resources/memory.md` (Pending Decisions), `resources/development-plan.md` (Risk Register §30), `DECISIONS.md` (ADRs).

## 3. Engineering follow-ups (no external blocker)

**Engineering — authorization**

- **No check that a declared capability is actually enforced.** SECURITY-AUDIT **M-7** found five
  ABDM M3 routes with no `requireCapability`, while the capability sat in the registry marked
  PLANNED. From the outside a capability nobody references is indistinguishable from one that is
  enforced. A build-time check — every `BUILT` capability in the registry is named by at least one
  route, and every `requireCapability` names a capability that exists — would have caught it, and
  would catch the next one. Cheap to write; the registry and the route table are both in code.

**Frontend**

- **React Compiler lint advisories are downgraded to warnings, not fixed.** A bump of `eslint-config-next` transitively enabled the `eslint-plugin-react-hooks` v6 React-Compiler rule suite, which flagged ~53 established, intentional patterns across all five apps as **errors** (SSR-safe theme init from `localStorage` on mount, and load-on-mount data fetching that sets a loading flag). To unblock CI they are set to **`warn`** in each app's `eslint.config.mjs` (`react-hooks/set-state-in-effect`, `preserve-manual-memoization`, `purity`) — the classic `rules-of-hooks`/`exhaustive-deps` stay **errors** (a genuine conditional-hook bug in `dashboard/page.tsx` was fixed, not silenced). Follow-up: a dedicated pass to resolve the warnings properly (lazy `useState` initialisers for theme, hoisting loading state, memoisation the compiler can preserve) and then restore them to `error`, or make a deliberate decision to keep the React Compiler rules off. There is one `react-hooks/purity` warning (`reports/page.tsx:39`, an impure call during render) worth checking first.

**Patient self-registration (ADR-056), follow-ups**

- **Nobody is told a request arrived.** The queue is a screen someone must remember to open. A notification to the front desk on submission — through the existing `NotificationService`, batched rather than one per scan — is the obvious next step, and is what stops a patient standing at a desk that never saw their details.
- ~~**No duplicate detection on approval.**~~ **Done 17/08/2026 (ADR-066).** Registration (by hand and by QR approval) now refuses a same-phone + same-name-or-DOB match with the candidate charts; the reviewer links the existing chart or knowingly registers anyway. Remaining refinement: fuzzy name matching (today the match is exact, case-insensitive) and an email-based match.
- **A rejected or abandoned request is kept indefinitely.** It holds a name, a phone number and an email for someone who may never become a patient. This needs a retention rule alongside the wider data-lifecycle work — it is the one place the platform holds personal data for a non-patient.
- **The QR is generated in the browser.** Fine for a poster; a server-rendered PDF (A4, with the hospital's branding and instructions) is what a hospital will actually want to hand to a printer.
- **Only one QR per hospital.** No per-branch token, so a multi-branch hospital cannot tell which entrance a person scanned. The column is there (`branch_id` convention) if that turns out to matter.

**Documents: letterhead image + page size (ADR-065)** — done 17/08/2026

- **The letterhead image prints once, at the top of the first page.** It matches the existing header behaviour, but a true pre-printed letterhead repeats on every page of a multi-page document. A running header (CSS `position: fixed` in `@page`, or a paged-rendering pass) is the follow-up; it was left out deliberately rather than half-built.
- **One page size per hospital, organization-wide.** Different document types cannot yet each choose a size (A5 prescriptions but A4 invoices) beyond the per-`PrintDocument` `pageSize` prop override in code — a per-document-type setting is additive if a hospital asks.
- **No image guidance beyond MIME + size.** Nothing checks the aspect ratio or resolution of an uploaded letterhead, so a tall or tiny image can look wrong on the page; a recommended dimension hint or a client-side check would help.

**Demo/test data (ADR-114)** — the dataset is in `docs/seed-data.md`

- **Five lifecycle states are written directly by the seeder because no product action produces them.** Each is a filter value the UI already offers, so the rows have to exist; the missing actions are the real gap: **appointment `no_show`** (mark a patient as not arrived), **invoice `void`** and **payment `refunded`** (cancel a bill, refund a collection — both need an audited reason and a rule about what a refund does to the invoice), **lab order `cancelled`** (withdraw an order that will not be collected), and **result flag `critical`** (a technician cannot mark a value critical; the flag is derived from the reference range only). Building any of these lets the seeder stop writing that row by hand.
- **No seed data for the clinic-flow workflow configuration or the vitals queue (ADR-113).** Only `BUILT` features are seeded (ADR-038); the hospital workflow config falls back to the platform default and vitals are recorded at consultation. Add the configuration rows and a `pre_consultation` vitals queue to the dataset in the change that ships that feature.
- **Uploaded files are not seeded** — patient documents, lab report PDFs, tenant logo/favicon and the letterhead image all mean writing binaries into object storage, which is environment configuration rather than database content. A small fixture-upload step in the seeder (a generated PNG/PDF through `FileStorageService`) would close the last "create it by hand first" gap on the patient detail page.
- **Audit history is inserted, not backdated.** `audit_log` is append-only at the database level, so the 30 days of history the date-range filter needs are written with their own timestamps rather than derived from the seeded actions. Acceptable, but it means the historical entries are representative rather than a true record of what the seeder did.
- **The seeded dataset has to be maintained with the product.** A new module or a new filter means a new entry in the seeders and a new row in `docs/seed-data.md`, in the same change — otherwise the dataset silently stops covering what it claims to.

- ~~**KNOWN FAILURE (30/08/2026) — one ABDM suite per full run dies in `beforeAll` with `Cannot activate "appointment": hard dependency "patient" is not entitled`.**~~ **Closed 01/09/2026 — it was never the harness.** Twelve consecutive full runs: the error occurred **zero** times.

**What actually fixed it, and it was product code.** Two bugs were stacked, both fixed in `c041785`:

1. **`hard dependency "patient" is not entitled` was a real onboarding bug, not concurrency.** `isEffective()` compared `tenant_entitlements.effective_from` — written by Postgres's `now()` — against the Node process's `Date.now()`. Those are two clocks, and Postgres routinely lands a millisecond or two ahead, so a module granted and _immediately_ re-read (exactly what `onboardTenant` does between `patient` and `appointment`) could read back as "not yet effective". The window is now evaluated in SQL (`effectiveNow()` in `entitlement.service.ts`), where the clock that wrote the row also reads it. **This would have failed a live tenant**, and grows more likely on faster hardware — the suite was the messenger, not the patient.
2. **`A tenant with code "X" already exists` was leftovers, not a race.** Eleven tests create a scratch tenant and clean it up after their last assertion, so a single failed assertion left the tenant behind and poisoned every run afterwards. `makeTenant` now calls `cleanupTenant(code)` first, so it is idempotent by construction.

**The `poolOptions` line never did anything.** `poolOptions: { forks: { singleFork: true } }` was added to `hms_backend/vitest.config.ts` on 30/08 to stop this, but `test.poolOptions` was **removed** in Vitest 4 — every run printed `DEPRECATED  test.poolOptions was removed in Vitest 4` and discarded the option. It cannot have "taken the run from two failures to one and then to zero"; that reading was noise. Migrated 01/09/2026: the dead option is gone and `fileParallelism: false` is the whole knob.

**And `fileParallelism: false` was serialising files the whole time**, contrary to what this entry assumed. In Vitest 4.1.11 the config resolver forces `maxWorkers = 1` whenever `fileParallelism` is false, and a project with `maxWorkers: 1` under the default `isolate: true` puts **every file in its own group** — one file per forked process, strictly sequential. The runs' own numbers agree: ~62s of import plus ~152s of tests against 233s of wall clock is not what parallelism looks like. So two `onboardTenant` calls were never overlapping, and `runWithTenant` could not have leaked context anyway: it takes a dedicated `pool.connect()`, sets `app.tenant_id` with `set_config(…, true)` inside the transaction, and binds Drizzle to _that_ connection.

**Also fixed 01/09/2026 — `vitest.config.ts` → `vitest.config.mts`.** `hms_backend` is CommonJS, so Node ≥22 loaded the `.ts` config through its own type stripping _as CJS_ and warned `ESM syntax in a file loaded as CommonJS` on every run. A full run is now warning-free. **`packages/ui/vitest.config.ts` still warns the same way** — the same one-line rename, not done here.

**Read this before you measure the suite again.** Six of the twelve runs were red and **not one of them was the suite's fault** — the working tree and the dev database were being written by another working session throughout. Runs 3–6 (14 → 14 → 30 → 51 failures) caught the vitals/workflow-config feature mid-landing: `emr.service.ts`, `vitals.service.ts` and `fhirBuilder.ts` switched to reading `patient_vitals` / `hospital_workflow_config` at 10:45–10:47, while `drizzle/0043_workflow_config_and_vitals.sql` was not written until 10:52:33 — so the runs in between failed with `relation "patient_vitals" does not exist`, confirmed by Postgres's own file-creation timestamps for those two tables (10:52:44). Run 11 (a `password_reset_tokens` count that moved 16 → 17 under a test asserting it would not) had a `db:seed` run inside it — `LOTUS` and `GREENLEAF` were created at 11:24:03 and 11:24:07, between the run starting at 11:22:29 and finishing at 11:26:32 — and `resetSeedData()` truncates **every** tenant-scoped table. Run 10 (`A tenant with code "CRITPATH"/"ABDMAPI" already exists` in two different files) is **inferred, not proven**: no foreign writer was caught inside its window, but `onboardTenant` passed its pre-check and then lost the unique index on the insert, and `cleanupTenant` had deleted `CRITPATH` moments before the pre-check found it — in a strictly sequential suite something outside the process has to have created both. **A full-suite run is evidence only if the tree and the database hold still for its four minutes**; otherwise it measures whoever else is typing.

**Where the suite stands:** the six clean runs were **62 files / 622 passed** and then **63 files / 642 passed**, 0 failed, 0 skipped, no warnings.

  **future** visits are charged: re-pricing a paid consultation would be a credit note, which is
  not built.
- ~~**Vitals have no workflow and no configuration.**~~ **Shipped 01/09/2026 (ADR-113).**
  `hospital_workflow_config` (branch-then-organization, platform defaults = the old behaviour) and
  `patient_vitals` (one row per observation, on the **visit** rather than the encounter). Vitals can
  be taken at the desk, in a derived vitals queue, or in the consultation; parameters are required
  or offered per hospital; `emr.vitals.view` / `emr.vitals.record` are their own permission pair so
  an assistant can take a blood pressure without the clinical note. Payment timing moved into the
  same table. **Still open here:** self check-in, payment _before_ check-in, and walk-in policy —
  this table is their home, but a setting is added when the workflow it configures is built.
  **Also not built:** a per-branch UI for staff working across hospitals (the configuration is
  branch-aware; the Portal has no branch switcher, ADR pending), and a vitals _trend_ view on the
  patient chart (readings are stored with time and person, nothing plots them yet).
- ~~**Check-in and booking are still two forms.**~~ **Shipped 01/09/2026 (ADR-115).** One
  `VisitWorkflow` component; both routes render it with a different starting timing, and the
  toggle is permission-aware. `arrival_type` (walk-in / appointment / follow-up) added to both
  `appointments` and `visits`, and appointments gained the department they never had. **Still
  open:** `caseType: NEW | EXISTING` is absent because cases do not exist — see the case item
  above; and the backends stay two endpoints on purpose (a future booking has no token, no
  invoice and no queue entry, so one endpoint producing both would be a worse abstraction than
  two honest ones). What is shared is the validation, and tests assert that symmetry.
- ~~**Self check-in does not exist.**~~ **Shipped 01/09/2026 (ADR-118)**, as an **announcement**
  the front desk confirms — ADR-056 does not permit a public path to write a visit, and the desk
  confirming is also the identity check. **Needs a decision from you:** whether to allow _fully
  automatic_ check-in with no desk step. It would mean a public endpoint creating a clinical
  record, so it needs **ADR-056 amended rather than worked around**, and the amendment has to say
  how identity is established without a human looking at the patient. Also not built, and cheaper
  to add if wanted: OTP on the kiosk (blocked on the same DLT registration as all SMS, I-1),
  identification by patient ID / QR / appointment reference, and any handling of a walk-in with no
  appointment — today they are told to go to the desk.
- ~~**The check-in screen has no patient-history panel.**~~ **Shipped 01/09/2026 (ADR-119).** The
  existing `PatientHistory` gained a `rail` layout and a Cases block and now renders beside the
  check-in form, each block permission-gated (reception sees cases / visits / bills / documents;
  the Consultations block needs `emr.encounter.view` and is absent without it). Documents needed a
  new table — `file_metadata` had **no patient link at all** — so `patient_documents` was added
  with the file store left generic. **Still open:** a document attached during check-in links to
  the patient, not to the visit being created (the visit does not exist while the form is open);
  there is no in-app preview, only a signed-URL tab; and no bulk or drag-and-drop upload.
- ~~**ABDM consent is not surfaced in check-in.**~~ **Shipped 01/09/2026 (ADR-120).** A third
  permission — `abdm.consent.status.view` — and a status-only endpoint returning states and counts
  with no records, no source hospitals and no requesting clinician, shown in the check-in rail.
  **Asking stays a doctor's act** (ADR-092 unchanged). The same change closed a real gap found
  while looking: `abdm.external_history` was marked PLANNED while M3 was built, and **no M3 route
  carried a capability gate** — a hospital entitled to ABDM for ABHA verification alone silently
  had a national records pull. All five routes are now gated, and the capability is BUILT.
  **Unchanged:** no record has been exchanged with ABDM in any environment, and production access
  still needs NHA functional testing, a WASA certificate and HTC approval.

**Engineering — ABDM**

- **No driving-licence identifier.** ABHA verification accepts `abha_number`, `abha_address`,
  `mobile` and `aadhaar`; enrolment is Aadhaar-only. A driving licence was asked about
  (02/09/2026) and is **not implemented anywhere** — not in `AbhaIdentifierType`, not in any
  provider method, not in the mock. Adding it is a new identifier type, a provider method on both
  the gateway and mock providers, its own OTP path, and NHA test cases; it is not a flag. Recorded
  so nobody reads the ABHA panel as supporting it.

**Engineering — clinical data**

- **A patient has no allergies field.** The patient-chart review (ADR-127) asked for allergies and
  clinical alerts at the top of the record, and the product cannot store either: `patients` carries
  a blood group and nothing else clinical. Blood group is surfaced as an alert badge; allergies are
  **not** shown, because an empty "Allergies" card promises a place to record something the system
  has no column for. Adding it is a schema change plus a place to enter it — the check-in form and
  the chart's edit form — and belongs with whatever ADR takes on clinical alerts properly.

**Engineering — access refusals**

- **Only the Portal's refusal panel explains itself.** The module-before-permission guard is in
  `@hms/client` and therefore applies to every frontend (ADR-126), but the _panel_ is per app by
  design (ADR-054) and `admin/components/Forbidden.tsx` still shows the generic message. The
  operator console refuses far fewer people and its audience knows the permission model, so this
  is a deliberate ordering rather than an oversight — move the Portal's panel into `@hms/ui` if a
  second app needs it, rather than copying it.

**Engineering — seeding**

- **The seed-idempotency suite leaves its fixture tenant behind.**
  `scripts/__tests__/seedIdempotency.test.ts` deletes everything it created except the tenant row
  itself: `audit_log` is append-only at the database level (invariant #6) and references
  `tenants` with ON DELETE RESTRICT, so a tenant that has been audited cannot be removed. CI's
  database is ephemeral, so this only affects a developer's local database, where it appears as
  one empty hospital named "Seed Idempotency Hospital". Fixing it properly means running the suite
  against its own database or schema; not worth it until a second suite needs the same thing.

- **The clinical story still cannot be topped up, only rebuilt.** `seedClinicalStory` runs once per
  tenant and is then marked done (ADR-122). If the dataset later wants a _new_ workflow state
  represented — a lifecycle the queue does not currently cover — an already-seeded staging database
  will not grow one; it needs `--reset`. The alternative (generating "the missing part" of a
  history) means diffing a narrative against a database, which is a much larger thing than it
  sounds. Revisit only if a QA gap actually appears.

## 4. Deferred on purpose (recorded so it is not re-litigated)

- **Public self-registration and payment-integrated self-serve plans** — Enterprise/Scale track (`resources/development-plan.md` §25, ADR-020). Onboarding stays operator-driven.
- **Microservices / Kubernetes / message broker** — needs a new ADR (ADR-001).
- **Named pricing tiers and published prices** on the marketing site — content guardrail until commercial terms exist.
- **HIPAA / certification claims** — never asserted; see U-5.
- **An in-app navigation guard on the consultation screen** (ADR-134). The screen guards a reload or a
  closed tab with `beforeunload` and states _Unsaved changes_ permanently in its sticky header, but
  clicking a sidebar link with unsaved work still loses it silently. Next’s App Router has no
  supported route-change guard, so doing it properly means a navigation-blocking pattern across the
  whole Portal shell — one decision for every long form, not a patch on this page. Raise it if a real
  user loses work this way.

**Engineering — QA documentation**

- **43 duplicate case IDs in `testcases.md`.** Found while adding the dropdown cases: `SEL-01` named
  two different tests, and so do 42 other ids across `ABDM`, `DOC`, `ADMIN` and others, out of 974
  cases. A tester reporting "SEL-01 failed" is ambiguous, and so is a fix that says it closed one.
  Not renumbered here: ids may be referenced in run sheets or defect reports outside this repo, so
  the renumbering needs a decision about what to preserve, not a script. The block added in this
  change continues the existing sequence rather than restarting it.
