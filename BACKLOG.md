- **Refresh rotation holds its transaction across the row update** (found while building the role dashboards, ADR-044). The client now sends a single in-flight refresh, which removes the storm, but the server still updates the `sessions` row inside a transaction that stays open across the round trip — a genuine burst (several tabs, or a slow network) can still queue on that row lock and drain the pool. Local reproduction: three `idle in transaction` sessions blocking six more, every request timing out. Belongs with the session-rotation work currently in flight; consider `SELECT … FOR UPDATE SKIP LOCKED` semantics, a shorter transaction, or accepting a rotation race and de-duplicating by token generation.

**Patient self-registration (ADR-056), follow-ups**
- **Nobody is told a request arrived.** The queue is a screen someone must remember to open. A notification to the front desk on submission — through the existing `NotificationService`, batched rather than one per scan — is the obvious next step, and is what stops a patient standing at a desk that never saw their details.
- ~~**No duplicate detection on approval.**~~ **Done 17/08/2026 (ADR-066).** Registration (by hand and by QR approval) now refuses a same-phone + same-name-or-DOB match with the candidate charts; the reviewer links the existing chart or knowingly registers anyway. Remaining refinement: fuzzy name matching (today the match is exact, case-insensitive) and an email-based match.
- **A rejected or abandoned request is kept indefinitely.** It holds a name, a phone number and an email for someone who may never become a patient. This needs a retention rule alongside the wider data-lifecycle work — it is the one place the platform holds personal data for a non-patient.
- **The QR is generated in the browser.** Fine for a poster; a server-rendered PDF (A4, with the hospital's branding and instructions) is what a hospital will actually want to hand to a printer.
- **Only one QR per hospital.** No per-branch token, so a multi-branch hospital cannot tell which entrance a person scanned. The column is there (`branch_id` convention) if that turns out to matter.

**Documents: letterhead image + page size (ADR-065)** — done 17/08/2026
- **The letterhead image prints once, at the top of the first page.** It matches the existing header behaviour, but a true pre-printed letterhead repeats on every page of a multi-page document. A running header (CSS `position: fixed` in `@page`, or a paged-rendering pass) is the follow-up; it was left out deliberately rather than half-built.
- **One page size per hospital, organization-wide.** Different document types cannot yet each choose a size (A5 prescriptions but A4 invoices) beyond the per-`PrintDocument` `pageSize` prop override in code — a per-document-type setting is additive if a hospital asks.
- **No image guidance beyond MIME + size.** Nothing checks the aspect ratio or resolution of an uploaded letterhead, so a tall or tiny image can look wrong on the page; a recommended dimension hint or a client-side check would help.

**Clinical-workflow hardening (ADR-066) — deliberate leftovers**
- ~~**Lab result file upload.**~~ **Done 17/08/2026 (ADR-070):** `lab_results.file_id` through the file module, attach on result entry, staff + patient-portal download via short-lived URLs. *Remaining refinement:* multi-analyte panels are still one value per order.
- **PHI read auditing.** `writeAudit` fires on every write, but viewing a chart, a result or an invoice leaves no trace — `GET`s are not audited anywhere. A clinical system ultimately needs read auditing (who opened whose chart); needs a sampling/volume decision before switching on.
- **Cross-service billing is not transactional.** Dispense and lab-collect deduct stock / move status in one transaction and bill in another; a billing failure in between leaves clinically-done-but-unbilled work (dedupe guarantees it can never double-bill, and check-in now compensates by deleting the visit). - **`cancelled` is still unreachable** for prescriptions and lab orders once an encounter is signed (while draft, removing the row is the cancel). A post-sign cancel endpoint (who may, and what it does to an already-billed line) is a product decision tied to the credit-note question (ADR-060 / E-6).
- **Appointment `no_show`** is never set — visits complete their appointment now, but nothing marks the patient who never arrived. Needs a cutoff rule (end of day? staff action?).
- **Token numbers serialize on a per-tenant advisory lock.** Correct and simple; if a very large hospital ever finds check-in throughput limited by it, move the counter to a `visit_counters` row per (tenant, date) with `UPDATE … RETURNING`.

**Security follow-ups after ADR-082 (the audit is closed; these are the next layer)**
- **A VAPT pass has still not happened.** Every finding in `SECURITY-AUDIT.md` was found and fixed by the people who wrote the code. The external OWASP Top 10 test (`resources/development-plan.md` §23) is what validates that, and it is a Stage 3 exit condition, not an optional extra.
- **Marketing is the one frontend without a nonce-based CSP** (ADR-082, static mode). It is safe while that site renders no user input and holds no session; wiring `ContactForm` (U-2) is exactly the change that ends that condition, so move `marketing` to nonce mode in the same task — and accept that its pages become dynamically rendered, or find a way to keep the form on an isolated route.
- **Lockout has no administrator override.** It self-heals in at most 15 minutes, which is why none was built. If a pilot hospital reports staff being blocked at shift change, the fix is usually a shared account, not a longer window — but an `org_admin` "unlock user" action (audited) is the obvious next step if it recurs.
- **Dev-tool advisories are reported by CI, not gated** (`npm audit` without `--omit=dev`): vitest/vite/esbuild currently report moderate-to-critical issues that are not reachable from production. They should still be cleared on the next dependency sweep rather than left to accumulate.
- **No automated coverage for the CSP itself in a browser.** `security.test.ts` proves the header we build; nothing asserts that a real page loads without violations. The Playwright smoke project is the natural home for "walk each app, fail on any CSP violation in the console".

**ABDM / ABHA — Milestone 1 (ADR-084)**
- **Existing tenants do not hold the four new permission keys.** `abdm.verification.perform`, `abdm.verification.link`, `abdm.facility.view` and `abdm.facility.manage` are in `@hms/permissions` and are granted to new tenants at onboarding, but tenants seeded before this change keep their old `role_permissions` rows. Re-seed the permission catalogue and the system-role grants for existing tenants (or grant per role by hand) before the feature is demonstrated on an older environment — otherwise the panel is invisible and the API answers 403, which looks like a bug and is not one.
- **`patients.abha_number` uniqueness is enforced in the application, not yet in the database.** `linkToPatient` refuses to attach an ABHA that already sits on another chart, and migration `0030` adds an expression **index** (not a unique one) on the normalised digits. It is not unique because the column predates the integration as free text, so existing rows may hold duplicates or malformed values and a unique index would fail the migration on live data. Follow-up: audit `abha_number` per tenant, clean what is wrong, then promote the index to `UNIQUE … WHERE abha_number IS NOT NULL`.
- **Endpoint contract reconciled 25/08/2026** against the official *Milestone 1 Postman Collection-18-08-2025* (143 requests). Five real deviations were found and fixed: the login-verify `scope` must be the same **two-element array** the OTP was requested with; `login/verify/user` authenticates with **`T-token`**, not `X-token`; ABHA-**address** verification is a different API family (`/v3/phr/web/login/abha/*`) and was pointing at the profile-login endpoints; the Scan-and-Share callback arrives at **`/api/v3/hip/patient/share`** (a path NHA appends to the registered bridge URL) with a **nested** payload, not our own path and flat body; and the exchange is **two-way** — the HIP must answer on `patient-share/v3/on-share` with the patient's token number, which was missing entirely. Everything else matched.
- **Live sandbox probe, 25/08/2026 (`npm run abdm:check -- --probe`):** the whole outbound pipeline is confirmed working against the real gateway — session, certificate, **PEM normalisation of NHA's bare base64 4096-bit key**, RSA/PKCS1 encryption, and a request NHA accepts and validates. A deliberately invalid Aadhaar came back `400 {"loginId":"Invalid LoginId","timestamp":…}`, which is NHA rejecting the *decrypted value*, i.e. proof the encryption is readable at their end.
- **RSA padding was wrong and it cost an afternoon (fixed 25/08/2026).** We sent `RSA/ECB/PKCS1Padding`; the ABHA APIs want **`RSA/ECB/OAEPWithSHA-1AndMGF1Padding`**. The failure mode is what made it expensive: a padding NHA cannot decrypt returns `400 {"loginId":"Invalid LoginId"}` — indistinguishable from a genuinely bad Aadhaar — so every identifier looked invalid, including well-formed mobile numbers. Settled by sending one checksum-valid, unassigned Aadhaar under three paddings: only OAEP-SHA1 got through to UIDAI (`422 ABDM-1204 "UIDAI Error code : 998"`). `npm run abdm:check -- --probe` still runs that comparison, so the next padding question is one command. Switching also removed a workaround in the mock provider, which had been unwrapping PKCS#1 blocks by hand because Node refuses PKCS#1 private decryption after CVE-2023-46809.
- **NHA's enrolment errors are keyed by field name**, not by `message` — `{"loginId":"Invalid LoginId"}`. The error parser now handles that shape (plus flat `message`, nested `error.message`, and `details[]`/`errors[]` arrays), so a rejection reaches the receptionist as NHA's own words instead of "request failed (400)". Bookkeeping keys like `timestamp` are skipped. Five shapes, all unit-tested.
- **Still unverified against a live sandbox call:** the enrolment and login *responses* on a SUCCESSFUL path. The collection pins the request shapes, which is what a wrong path or scope breaks; the parsers are deliberately tolerant of response variation, but only a real run confirms which fields actually come back.
- **Bridge registration commands in NHA's onboarding email are outdated V1.** The V3 collection uses `PATCH https://dev.abdm.gov.in/api/hiecm/gateway/v3/bridge/url`, and service registration is on the **facility registry host** — `POST https://facilitysbx.abdm.gov.in/v1/bridges/MutipleHRPAddUpdateServices` (NHA's own spelling) with `{facilityId, facilityName, HRP:[{bridgeId, hipName, type:"HIP", active:true}]}`. The email's `type: "HEALTH_LOCKER"` example is a different participant type. Paths recorded in `abdm.constants.ts` → `BRIDGE_ADMIN`.
- **`facilityId` format is the registry's** (`IN0710……` in NHA's example), and it is what a hospital enters in Hospital configuration → ABDM / ABHA.
- **Sandbox credentials issued 25/08/2026** — NHA created the bridge and sent a client (bridge) ID and secret. **Not recorded here or anywhere in the repository**: they belong in `hms_backend/.env` locally and in the deployment secret store for staging. `npm run abdm:check -w hms_backend` proves the pair works against the real gateway without printing it, which is also the evidence NHA's ticket asks for. **Verified 25/08/2026:** session issued (bearer, `expiresIn` 1200s) and the RSA public certificate fetched from the ABHA host — so the credentials, both hosts and the encryption path are confirmed. The 1200s TTL is comfortably inside the session cache's design (refresh 60s before expiry), so the token is fetched roughly once every twenty minutes rather than per request.
- **No end-to-end run against the real ABDM sandbox yet.** Everything is proven against the mock provider (64 automated tests). Sandbox OTP limits are a few per number per day, so plan the manual pass rather than improvising it.
- **The bridge URL cannot be registered until the staging API has valid TLS.** NHA requires an HTTPS endpoint with a valid certificate (`PATCH https://dev.abdm.gov.in/api/hiecm/gateway/v3/bridge/url`), which is blocked on issuing Let's Encrypt certificates for `api-staging.nirogix.com` — item **I-5** above. Register the **base** URL only (`https://<api host>`): the gateway appends `/api/v3/hip/patient/share` itself, which is why that route is mounted outside `/api/v1`.
- **The HIP service still has to be added to the sandbox mock facility registry** (`POST /gateway/v1/bridges/addUpdateServices`, `type: "HIP"` — NHA's example says `HEALTH_LOCKER`, which is a different participant type and is not what we are). The service id chosen there becomes the facility id a hospital enters in Hospital configuration → ABDM / ABHA. Until it exists, Scan and Share cannot be tested against the sandbox; the Aadhaar and identifier flows can.
- **NHA's example curl commands omit the `Authorization` header.** All three bridge-administration calls need `Authorization: Bearer <session token>` from `POST /api/hiecm/gateway/v3/sessions`; without it they answer 401 and look like a credential problem.
- **Facility QR payload is entered by hand.** The hospital pastes the HFR QR content into Hospital configuration → ABDM / ABHA; we render it. Fetching it from the Health Facility Registry directly is M4 (NHPR) territory and out of scope.
- **The ABHA card is downloadable during a verification only.** It is streamed from ABDM and never stored, so it is unavailable from the patient chart afterwards. If the desk needs it later, the decision to attach it to the chart (and therefore to store a document carrying the patient's photo) has to be taken deliberately.
- **M2 (HIP — linking care contexts) and M3 (HIU — consented record fetch) are not built and must not be started without the legal and compliance review** the development plan already requires (§36). The linking token is captured and encrypted now because ABDM only offers it at verification time; nothing consumes it.
- **Going live is an organizational path, not a development one:** NHA-empanelled functional testing → internal NHA demo → WASA "Safe to Host" certificate (STQC or CERT-In empanelled) → HTC approval via the sandbox portal's Exit Form. Chargeable, several weeks, and it should be budgeted now rather than discovered later. V1/V2 implementations are rejected at that review; this build is V3 only.
- **`ENCRYPTION_KEY` becomes a production-critical secret.** ABDM tokens are encrypted at rest with it; rotating it invalidates existing ciphertext. It needs to be in the deployment secret store and in the backup/restore runbook before ABDM is enabled anywhere real.
