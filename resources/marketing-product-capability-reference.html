Binding rule — read before writing any copy

Marketing must never advertise a capability as available unless its status in this document is BUILT / AVAILABLE.

IN DEVELOPMENT, PLANNED, FUTURE / CONSIDERATION and NOT AVAILABLE features must never be presented as functionality a customer can use today. They may be discussed as roadmap only where the marketing strategy explicitly allows roadmap communication, and only in those words.

Every public claim must be traceable to a row in this document, and through it to the implemented product or the approved product documentation. If a claim cannot be traced here, it does not ship — ask engineering to add the row first.

Golden rule. If the product cannot currently do it, marketing must not sell it as if it can. If development changes what the product can do, this document changes in the same development task.

This document is deliberately blunt about gaps. A gap is not a weakness in the sales story — an accurate story about a working clinic-core platform closes deals that an inflated one loses at the demo.

Status legend

Every feature, module, capability, workflow, integration and major UI capability in this document carries exactly one of these five statuses.

Built / Available

Implemented and usable in the product right now. Marketing may describe it as Available. Never applied on the strength of a plan, a design or a partially-wired screen.

In development

Actively being implemented, not yet fully usable. Never advertised as available. May be described as In Development where that is appropriate.

Planned

Approved and on the roadmap; implementation not started or not sufficiently complete. Never presented as an existing capability. May be mentioned as Planned where roadmap communication is allowed.

Future / consideration

Under consideration or belonging to a later phase, not committed. Never advertised as a product capability, and never given a date.

Not available

Explicitly not supported. Marketing must never claim or imply support, including by omission, analogy or an implying visual.

How a status is decided A status is never assigned from assumption. It is set from the current implementation in this repository, cross-checked against resources/projectrequirementdoc.md (scope), resources/architecture.md (design), resources/phases.md and resources/development-plan.md (sequencing) and BACKLOG.md (what is knowingly open). When the implementation changes, the status changes with it.

Isolation uses PostgreSQL row-level security on every tenant-scoped table, with an application-layer tenant filter on top as defence in depth. Authentication & sessions

Built

Email and password sign-in with short-lived access tokens, server-side revocable sessions, and self-service password change.

Purpose
Prove who a user is and keep the session safe
Users
Every role
Phase

RBAC, Audit, Security

Passwords are stored with bcrypt and held to one policy wherever they are set — by the user, by an administrator, or through a reset link. The access token is held in memory only and never in browser storage; the refresh token is an http-only, path-scoped cookie that is Secure in production. Sessions are database rows, so they can be revoked — and a password change revokes every one of that user's sessions. Login is rate-limited, locks an account after repeated failures, ends after fifteen minutes of inactivity, and is audited throughout.
