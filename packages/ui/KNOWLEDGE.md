# @hms/ui — KNOWLEDGE.md

The shared design system for the Nirogix monorepo. Consumed by `hms_frontend` (Portal) and `marketing`. Read after root `CLAUDE.md`.

## What's here

- **`src/styles.css`** — the **single design-token layer** (`--hms-*`: colour, radius, type, shadow) with **Light default (`:root`) + Dark (`[data-theme="dark"]`)**, plus overridable brand tokens (`--hms-brand*`) and the canonical CSS for every primitive. Imported once by the app: `import '@hms/ui/styles.css'`. Includes the **global scrollbar treatment** (thin, token-coloured thumb, transparent track — Firefox properties + WebKit pseudo-elements) that every scroll container in every consuming app inherits in both themes; marketing's `--hms-* → --mk-*` bridge re-colours it for that site automatically.
- **Primitives** (`src/components/`, all token-only — no hardcoded colour/spacing/radius/type): `Button`, `Field`, `PasswordField`, `Card`, `Badge`, `Alert`, `Spinner`.
- **`Field`** takes `label`, `error` and `hint`. `error` replaces `hint` when both are set, so a field never shows two competing messages, and whichever renders is wired to the input through `aria-describedby`.
- **Column `align` governs the heading and the cells together.** The class goes on the `th`, and a non-left alignment makes the sort control fill its cell so it can justify. Reserve `right` for magnitudes compared down a column (money, counts) and the actions column — a label containing a digit reads better left.
- **`Dialog`** is the one modal (ADR-060). It portals to `document.body` so no parent’s `overflow` or stacking context can clip it, locks background scroll through `useScrollLock`, traps Tab, closes on Esc and the backdrop, and returns focus to whatever opened it. Sizes are `sm` (a confirmation), `md` (a short form), `lg` (a record with sections); the body scrolls when the content outgrows a short viewport so the title and actions stay put. **While `busy`, Esc and the backdrop stop closing** — a dialog that vanishes mid-save leaves the user unsure whether their edit was written. **Focus opens on the first control in the body, not the panel**: the close × sits in the header and therefore comes first in DOM order, so "first focusable" would land an edit dialog on Close and the next keystroke would dismiss it.
- **`ConfirmDialog` is built on `Dialog`**, not beside it — one modal implementation, one set of focus and scroll behaviour to keep correct. What remains in it is only what makes a confirmation: the warning icon, two buttons, `role="alertdialog"`, and no close × (a confirmation is answered, not dismissed).
- **`Textarea`** is the multi-line counterpart to `Field` — same `label` / `error` / `hint` contract, same `aria-describedby` wiring, same `hms-input` styling. Use it rather than a bare `<textarea>` so a form can mix single and multi-line inputs without a second set of conventions.
- **`Select`** is the one dropdown (ADR-112). Never a native `<select>`: it cannot show a second line, cannot be searched, renders in the browser's chrome rather than these tokens, and on a phone hands the user an OS wheel that ignores all of it. An option carries a `label`, an optional `description` (second line), an optional `meta` (right-aligned — a fee, a count), an `icon`, a `group`, and `keywords` the search should also match. Search appears automatically past seven options (`searchable="auto"`), and matches whitespace-separated terms in any order. **The panel is portalled to `document.body` and positioned in viewport coordinates**, recomputed on capture-phase scroll and on resize, so no ancestor `overflow` — a dialog body, a scrolling table container — can clip it; it flips above the trigger when the space below is short and is bounded by the room actually available. The trigger truncates a long label with an ellipsis and keeps the full text in `title`; the open list wraps instead, because a half-shown drug name is what makes the wrong one get picked.
- **`PasswordField`** is the **required** control for every password input across the platform (login, reset, change-password, admin user forms) — it carries a built-in show/hide (eye) toggle. Never use a bare `<input type="password">`; always reach for `PasswordField` so the reveal affordance is consistent everywhere.
- **The Standard DataTable system** (`src/components/data-table/`, ADR-029) — `DataTable` on a **TanStack Table** core, following the shadcn/ui Data Table pattern, plus `DataTableToolbar`, `DataTablePagination`, `DataTableColumnHeader`, `DataTableViewOptions`, `DataTableFacetedFilter`. Sorting (multi-level, Lucide indicators), search, faceted filters, column visibility, row selection, configurable page sizes (10/20/50/100), sticky headers, contained horizontal scroll, skeleton/empty/error states, optional URL state, and a `server` mode that delegates paging/sorting/search to the API. Columns are a **superset of the original `{ key, header, cell }`** shape — add `sortable` / `filterable` / `hideable` / `accessor` to opt in — so existing screens kept working when the engine changed.
- **`Menu` / `MenuItem` / `MenuCheckboxItem`** — the one dropdown primitive (Esc + outside-click close, arrow-key roving focus); `MoreActions` and `ConfirmDialog` (focus-trapped, scroll-locked) build on it. `triggerBase` swaps the trigger's base classes so a row action's "…" matches the other icon actions.
- **The Action column** (`src/components/table-actions/`, ADR-039) — `actionsColumn()` defines the column (last, right-aligned, headed "Actions", never sortable or hideable); `TableActions` groups up to three inline icon actions built from `ViewAction` / `EditAction` / `DeleteAction` / `ToggleAction`, plus `TableAction` for a module's own operation ("Check in", "Start consult", "Revoke module"), with `MoreActions` for the overflow. The components own the icons, sizing, hover/active/focus, tooltips, accessible names, `disabledReason`, loading spinner, confirmation, and permission gating (`permitted={false}` renders nothing); a page passes intent only. `DeleteAction` always confirms; `ToggleAction` is a real `role="switch"`. Supersedes the old `ActionMenu`, which was migrated into `MoreActions` and deleted.
- **`EmptyState` / `ErrorState` / `Skeleton`** — the shared states, used by the DataTable and directly by pages.
- **Charts** (`src/components/charts/`, ADR-043) — `AreaChart` (hover cursor that snaps to a real point), `BarChart` (stacked), `StatCard` (KPI tile with optional delta + sparkline), `UsageBar` (labelled proportion, a real `progressbar`). Dependency-free SVG/CSS on the tokens; the caller passes colours as tokens, and `geometry.ts` holds the maths so it can be unit-tested away from the DOM. Every chart repeats its numbers in a visually-hidden table.
- **Base UI popup gotchas** (learned building the date picker, worth knowing before styling another): the **z-index belongs on the `Positioner`**, not the `Popup` — the popup is `position: static` and z-index is inert on it, so a sticky table header will paint over an open popup. And style the open/closed state from **`data-closed`, never `data-ending-style`**: Base UI unmounts only when the exit animation completes, so a popup with no transition never closes, and one that closes instantly (`data-instant`) leaves `data-ending-style` behind, which then renders the *next* open invisible.
- **Date/time entry** (`src/components/datetime/`, ADR-048) — `Calendar` (shadcn's Base UI calendar on `react-day-picker`, restyled onto the tokens), `DateField` (typed and picked in `DD/MM/YYYY`, emits ISO, rejects impossible or out-of-range dates), `TimeField` (`hh:mm` + AM/PM toggle, emits 24-hour), `DateTimeField` (both, emits one ISO instant). `react-day-picker` is a dependency of this package, not the apps; its internal `date-fns` never formats anything the platform displays.
- **Date/time display** — `DateDisplay` / `TimeDisplay` / `DateTimeDisplay` (ADR-046): `DD/MM/YYYY`, `hh:mm AM/PM`, `DD/MM/YYYY, hh:mm AM/PM`, each emitting `<time datetime>` with the ISO value. `badge` renders the meridiem as a chip (`.hms-meridiem`) for schedules and pickers. Formatting itself lives in `@hms/utils`; these are the render layer.
- **The document/print kit** (`src/components/print/`, ADR-047) — `PrintDocument` (branded header, title, reference, meta, footer, confidentiality notice) plus `PrintSection` / `PrintFields` / `PrintTable` / `PrintTotals` / `PrintSignatures` / `PrintNote` / `PrintToolbar`. Owns the page geometry (a `PAGE_GEOMETRY` table maps `A4`/`A5`/`LETTER`/`LEGAL` to a sheet width and an injected `@page size`; A4 is the default — ADR-065), `@page` margins, repeating table headers across pages, break-avoidance and print colour retention. Branding is passed in — the kit never assumes whose document it is. `DocumentBrand` also carries the tenant's letterhead (ADR-056, ADR-065): `headerLine` prints between the hospital's name and its address block, `footerLine` prints full-width **above** the platform's confidentiality notice rather than replacing it, and `PrintSignatures` fills a line from `signatoryName`/`signatoryDesignation` only where that line sets `useDefaultSignatory` — opt-in, so a patient's signature line is never filled in with the hospital's signatory. When `letterheadImageUrl` is set the image renders full-width and **replaces** the constructed name/logo/contact header, with the document title moving to a bar beneath it; `pageSize` (prop, else `brand.pageSize`, else A4) drives the sheet width and the printed page size. `.hms-qr-poster` styles the patient-registration poster (ADR-056), which is a document like any other rather than a printed screenshot.
- **`BrandMark`** — the Nirogix mark (N monogram on a rounded tile), drawn from `--hms-brand` / `--hms-brand-fg`. One implementation for the Portal shell, the login card, the marketing header and footer; both apps' `app/icon.svg` favicons repeat the same geometry with literal colours, since a favicon renders outside the token scope.
- **`cn`** — tiny classname joiner (no clsx dependency).
- Behaviour helpers: `SmoothScroll` (Lenis), `useScrollLock`, `BackToTop`, `LottiePlayer`/`LottiePreloader`, `lottieRecolor`.
  **`SmoothScroll` is the marketing site's alone (ADR-111)** — the four application portals scroll natively. The other two are written to work either way: `useScrollLock` pins the document itself and compensates for the scrollbar width (so an opening dialog does not shift the page sideways), stopping Lenis only where an instance exists; `BackToTop` takes its visibility from the native scroll position, and returns through Lenis where Lenis is running.

## `Toaster` / `toast()` — the one notification surface

**React Toastify** (ADR-057, superseding the shadcn/Base UI Toast of ADR-032), wrapped so that nothing outside this package knows which library is underneath. Never build a second one, and never import `react-toastify` anywhere else.

- **`src/toast.tsx`** — the adapter. With `Toaster` it is one of only two files that import `react-toastify`, both in this package. It owns the call-site API (`toast(msg)` / `toast.success|error|warning|info|loading(...)` / `toast.dismiss(id?)` / `toast.update(id, patch)` / `toast.isActive(id)`), the per-variant durations (success and info 5s, warning 7s, error and loading persist), the per-variant ARIA role (`alert` for error and warning, `status` for the rest), and de-duplication. It is callable with **no React mounted**, because the shared API client raises every notification from outside React.
- **De-duplication uses the toast id.** The de-dupe key *is* the id, and liveness is read back with `toast.isActive`, so a retried request refreshes its toast rather than stacking a second one — and a toast the user dismissed is genuinely gone, so the same message can be raised again. The previous implementation kept its own key→id map, which could hold an entry for a toast that no longer existed.
- **`src/components/ToastBody.tsx`** — everything visible: the Lucide icon per variant, the title, the description, an optional action, and the close control. **Status is never carried by colour alone** — each variant has a distinct icon *and* a title in words, so it survives greyscale and a screen reader reading the text unstyled.
- **`Toaster`** — mount once per app in the root layout. **Top-right, below the app bar**, `limit` caps the visible stack at 4 and the rest queue, pause on hover and on tab blur, a close button, and a progress bar on anything timed. It imports the library's stylesheet itself so an app cannot forget it.
- **Theming is one block of CSS.** Every `--toastify-*` variable is re-pointed at `--hms-*` in `styles.css`, so Light/Dark and the active tenant accent apply with nothing else to change, and an app that scopes the tokens differently (marketing's `--mk-*`) is served by the same mapping. The library's own `theme` prop is pinned to `light` and neutralised — there is one palette definition, not two. **No colour is ever passed to a toast call.**
- **Watch the library's own media query.** React Toastify's `<=480px` rule sets `top`, `left` and `width` as literal values rather than through its variables; the mobile block in `styles.css` overrides the properties directly, and without it a toast on a phone sits at the very top and covers the app bar.

## Rules

- No component hardcodes a raw visual value — everything derives from `--hms-*` (resources/rules.md → Design System). Theme switches by toggling `data-theme` on `<html>`; tenant branding overrides `--hms-brand` at runtime.
- **`--hms-brand` is the only brand value ever set** (ADR-040). `--hms-brand-hover` and `--hms-brand-subtle` derive from it with `color-mix` (darkening on Light, lightening on Dark), and `--hms-ring` is `var(--hms-brand)` — so one override re-skins resting, hover, pressed, focus and tinted states everywhere. Never write a second brand literal, and never set `--hms-brand-hover` from application code.
- **A consuming app maps these tokens onto its own scope, once.** The marketing site defines `--hms-*` in terms of `--mk-*` in its `globals.css`, so shared components (BackToTop, BottomNav, NavDrawer) follow the marketing accent and its platform-branding override instead of the Portal defaults.
- Consumed from **source** via the app's `transpilePackages` (no build step). React 19 is a peer dependency.
- Adding a token → add it to `styles.css`; the consuming app maps it into Tailwind's `@theme` if it needs a utility for it.

## Verify / build

- `npm run typecheck -w @hms/ui`. Visual verification happens in the consuming app in **Light + Dark** and under a non-default brand.
