# CLAUDE.md — Nirogix Monorepo Index

Root guide for humans and AI agents working in this repository. **Read this first**, then the relevant app/package `KNOWLEDGE.md`, then its `DONE.md`, then the source.

> **Nirogix** is an enterprise Hospital Management System (multi-tenant SaaS) by Takoriya Technology LLP, at `nirogix.com`. The authoritative product/architecture/rules live in `resources/`. This file indexes the codebase and the conventions every change must follow.

> **Naming (ADR-041).** The product is **Nirogix** in every user-visible string, document, and configuration. Internal identifiers keep their `hms` prefix on purpose — the `hms_backend/` and `hms_frontend/` directories, the `@hms/*` package scope, the `--hms-*` tokens, and the `.hms-*` class names. Do not rename them opportunistically. The frontends added in ADR-051 are named for their audience (`admin/`, `patient/`, `aiportal/`) and carry no prefix. In marketing copy, "HMS" appears only as the industry search term for _hospital management system_, never as the product's name.

## Monorepo layout (ADR-013 — kept folder names)

**Five frontends, one backend (ADR-051).** Each frontend serves one audience and owns nothing but rendering; the backend is the single source of truth for authentication, authorization, tenant resolution, permissions, business logic and audit. A frontend guard is UX, never security.

```
hms_backend/            Node.js + Express + TypeScript API — the only place any boundary is enforced
marketing/              Next.js public marketing/SEO site (:3000 → nirogix.com)
hms_frontend/           Next.js Nirogix Portal — hospital staff only (:3001 → portal.nirogix.com)
patient/                Next.js patient portal — verified patients (:3002 → patient.nirogix.com)
admin/                  Next.js platform administration — vendor operators (:3003 → admin.nirogix.com)
aiportal/               Next.js AI Portal — authorised staff + operators (:3004 → nirogix.ai)
packages/types          @hms/types — shared TS types & API contracts (backend + every frontend)
packages/client         @hms/client — shared frontend foundation: HTTP core, session context, guards (ADR-054)
packages/ui             @hms/ui — design tokens (Light default + Dark), primitives, Standard DataTable
packages/config         @hms/config — shared tsconfig/lint/build config
packages/utils          @hms/utils — shared framework-agnostic utilities
packages/permissions    @hms/permissions — dot-hierarchy permission keys (shared FE/BE)
resources/              Product/architecture/rules/plan docs (source of truth)
```

Tooling: **npm workspaces + Turborepo** (ADR-014). Root scripts: `npm run install:all | dev | build | lint | test | typecheck | format` (turbo-driven). Node ≥20, npm ≥10.

## Tech stack

- **Backend:** Node.js + Express + TypeScript; versioned REST under `/api/v1`; Zod validation; OpenAPI/Swagger from route definitions.
- **DB:** PostgreSQL (system of record) via **Drizzle ORM** (ADR-012); Redis for cache + BullMQ job queue.
- **Frontend:** Next.js (App Router) + TypeScript for both Portal and Marketing.
- **Infra:** E2E Networks (India-resident), managed PostgreSQL, E2E Object Storage, Cloudflare edge; Nginx + PM2; GitHub Actions CI/CD.

## Non-negotiable invariants (see `resources/memory.md`)

1. **Tenant isolation** via PostgreSQL RLS. Tenant A must never access Tenant B's data — tested on every module. Tenant context comes only from the authenticated session, never client input.
2. **Frontend visibility is never security.** Every protected endpoint independently re-checks, in order: `authenticated → tenant entitled to module → user permitted the action → business logic`.
3. **Explicit DENY always overrides GRANT**, at every level.
4. **Permission cache** never outlives the earliest `valid_until` among its temporary overrides; `revoked_at` triggers immediate targeted invalidation (ADR-010).
5. **Core clinical entities stay strongly typed** — no EAV. Specialty variation uses configurable form templates.
6. **Entitlement, permission-override, and audit records are never physically deleted.**
7. **Modular monolith** — no microservices/K8s/broker without a new ADR. Cross-module calls go through domain events or defined service interfaces.
8. **Financial Transaction Infrastructure** is the only place invoice/payment/tax/receipt/ledger primitives live; billing modules consume it.

## Conventions

- **API:** one consistent error shape `{ error: { code, message, details? } }`; every request Zod-validated; idempotency keys on payments/invoices/bookings/notifications/external calls; `/api/v1` versioned.
- **API docs (mandatory):** every `/api/v1` route is documented in OpenAPI, generated from Zod via `zod-to-openapi` in `hms_backend/src/openapi/` — never hand-written. Swagger UI at `/api/v1/docs`, spec at `/api/v1/openapi.json`; server URLs come from config, never hard-coded. `npm run openapi:validate` gates undocumented/invalid APIs in CI. Docs ship in the same change as the endpoint. See `resources/rules.md` → API Documentation Rules.
- **DB:** every tenant-scoped table has `tenant_id` + an RLS policy; nullable `branch_id` (NULL = org-wide); migrations additive & reversible; optimistic locking on concurrently-edited records.
- **Authorization:** permission keys are dot-hierarchy (`module.submodule.page.action`) declared in `@hms/permissions`; routes gated by `requireModule()` then `requirePermission()`.
- **Specialty & modules (binding — ADR-083):** the platform is configurable-per-specialty, never a hard-coded workflow per doctor, and **specialty is never a security boundary**. The effective feature set for a user is the **intersection** _tenant enabled modules ∩ provider specialty module set ∩ user permissions_ — specialty narrows the view, it can never widen access. The enforced chain stays `requireModule()` then `requirePermission()`; the sidebar, dashboard, quick actions, forms, filters, reports and settings only _reflect_ that boundary (module-aware nav is UX, not security). A specialty maps (as seeded data, `SPECIALTY_MODULE_MAP`) to a required/recommended/optional module preset applied at onboarding and then org-overridable — a default, not a lock. Specialty-specific clinical features are **independent modules** (module-catalog entry + `requireModule`+`requirePermission` + a nav item carrying its module + optional `specialty_form_templates`, no EAV on core entities); the shared patient/appointment/OPD/EMR/prescription/billing/auth/user-management core is never branched on specialty. Adding a specialty later is a `SPECIALTY_CATALOG` + `SPECIALTY_MODULE_MAP` row, plus one new module only when a genuinely new feature is required.
- **Module & capability engine (binding — ADR-085, extends ADR-083):** entitlement has **two tiers — module and capability** — both runtime-checked, neither a security bypass. Effective features = _tenant modules ∩ tenant capabilities ∩ provider specialty ∩ user permissions_; the enforced chain is `requireModule()` → `requireCapability()` → `requirePermission()`. A capability is _what the system supports_, a permission is _who may use it_ — a hospital disabling a capability overrides every role that holds its permission. There is **one canonical `Domain → Module → Capability` registry** shared backend + frontend (extends `moduleCatalog.ts`), each entry carrying a lifecycle status; **only a `BUILT` entry is entitled to a real screen/API or marked available in marketing (ADR-038)** — the registry may describe an unbuilt module, which is not a claim it exists. **Every new module is built to the engine** (registry entry + module/capability gate + module-aware nav + shared-domain/event interconnection, never a private reimplementation of Patient/Appointment/Payment — one Payment, invariant #8); existing modules are retrofitted onto it without rewrite. Disabling a module or capability hides and protects it but **never deletes historical records** (invariant #6); every toggle is audited.
- **UI:** follow `resources/DESIGN.md` (the canonical design system — deep-teal signature, cool-neutral surfaces, Lucide icons). No component hardcodes color/spacing/radius/typography — use `@hms/ui` tokens; all tabular data uses the shared DataTable; verified in Light + Dark and under a non-default tenant's branding before "done".
- **shadcn/ui (binding — ADR-028):** installed in both frontends as a **CLI + reference layer only**; `@hms/ui` stays the canonical kit. `shadcn add` output lands in `hms_frontend/components/ui/` and `marketing/components/shadcn/`, and must be restyled onto `--hms-*` / `--mk-*` and checked in both themes before it ships. Both apps map shadcn's semantic variables onto the design tokens and drive `dark:` from `data-theme`, so generated components are on-brand by default. The `shadcn` agent skill lives in `.agents/skills/`.
- **Reusable UI (binding — ADR-029):** build once, configure everywhere. Every tabular view uses the **Standard DataTable** from `@hms/ui` (TanStack core, shadcn pattern) with a per-module column/filter configuration — never a module-specific table, toolbar, pagination, column-visibility, filter, action menu, or state component. Destructive actions use `ConfirmDialog`, and blank/failed/pending views the shared `EmptyState` / `ErrorState` / `Skeleton`. Check `@hms/ui` before building any UI; a pattern that appears twice gets extracted.
- **DataTable defaults (binding — ADR-029, ADR-063):** every table shows **all applicable columns by default** — `defaultHidden` is an exception that needs a stated UX/performance reason, never a habit — and the user keeps the column-visibility control to hide/show by hand. A table provides the **structured filters its module needs** (not a bare search box where the data is structured), through the shared toolbar controls, in the fixed order **Search → Filters → Sort → Column visibility → Actions → Pagination**, with clear labels, multi-select / date-range / amount-range where they fit, clear-all, active-filter indicators and a proper empty state. Large datasets filter **server-side** — the `server` contract carries active filters alongside page/size/search/sort — never by pulling the whole table into the browser. No one-off tables.
- **Dashboard stat cards (binding — ADR-043, ADR-062):** every KPI tile is the shared `StatCard` from `@hms/ui` — never a hand-rolled card. A trend's colour is decided by what the metric **means** (`invertDelta`: wait-time down is good, revenue down is bad), never by the sign; a delta is passed only when a real prior period exists. A card is **clickable only when a click has a genuine destination** (Total Patients → Patients table; Today's Appointments → Appointments filtered to today), and then it is a real link/button with hover / focus-visible / keyboard / active states and an accessible name — never made clickable for visual uniformity. Permission-gated: a tile the user may not act on is not rendered.
- **Seeded data that ages (binding — ADR-133):** anything written relative to **today** — a queue, an arrivals board, "seen today", a vitals queue — is stale tomorrow, so it is seeded differently from history. A **past runs once** behind a marker (ADR-122); the **present is rebuilt on every run**, guarded on the day itself ("does today already have one?"), so re-running is free and an environment seeded last week still has a live board this morning. A screen that is empty in **every** environment, always, is a seeding gap rather than a feature — blank-because-nothing-happened is indistinguishable from blank-because-broken. And a **collision degrades rather than aborts**: a taken slot becomes a walk-in, a patient already in the queue is skipped, an arrival without a booking is still an arrival, each counted in the seed report.
- **Multi-step external flows (binding — ADR-130):** where a flow spans several calls to an external system (ABDM verification and enrolment), **an absent field means "this call did not say", never "this value is empty"** — each response is _merged over_ what is already known, per field, skipping null, undefined and blank, and the newest response is never treated as the whole answer. Persist what a step gives you even when you cannot use it yet (an account list is often the only description of that person the flow will produce), never split an external register's single `name` on a space, and keep the **test double no kinder — and no more agreeable — than the system it stands in for**: a mock that answers more fully than the sandbox, or echoes back the value you asked for instead of the one it holds, hides precisely this class of defect. Also (ADR-131): **use what you already have as soon as you have it** — a profile that has arrived fills the form now, and a further step confirming one field is not a reason to withhold the other ten; **one request, one error**, because two calls sharing a `try` blame the step that succeeded; **parse a tri-state as a tri-state**, since flattening "not stated" into `false` invents a response the caller then acts on; and **decide from the data where the data can decide**, treating a provider's flag as a tie-breaker rather than the authority.
- **Configuration read keys (binding — ADR-129):** a permission named for the screen that _edits_ a setting is the wrong key for the screens that merely _read_ it. Where a configuration governs a form — where vitals are taken, when the fee is due, which vocabulary a dropdown offers — **every role that uses the form holds the read key**, or the form 403s against the settings that describe it. Keep the pair (`…​.view` reads how the hospital runs, `…​.manage` decides it, and only the administrator holds the second); never "fix" it by dropping the permission from the route, because a page guard on a key no endpoint enforces is a boundary in name only. And **a failure the caller already handles raises no toast** — use ADR-057's `feedback: false` where the screen falls back to a documented default, or an error appears beside a form that works.
- **Page actions (binding — ADR-128):** a page's **primary action lives in its `PageHeader`, top-right, and nowhere else** — _Register patient_, _Book appointment_, _Check in_, _New invoice_, _Add service_ are all in the same place on every screen, so the position is learned once rather than hunted for per page. The Standard DataTable has **no toolbar action slot**: its toolbar is Search → Filters → Sort → Column visibility → Pagination (ADR-029) and holds nothing else, so a create button has nowhere else to go. Where a page has several actions, supporting ones come first and the primary is **last** (right-most): `ghost` for navigating away, `secondary` for a side task like _Print / PDF_, the default variant for the action the page exists for. Gate it in place with `<Can perm={…}>` — an action the user may not perform is not rendered, never disabled and never relocated. Row-level actions stay in the Action column (ADR-039); an empty state may **repeat** the header's action (`emptyAction`), which is a repeat, not a second home.
- **Form & input behaviour (binding — ADR-127):** **typing must never move the caret** — a focus trap depends on whether it is _open_, never on a callback prop, because callers pass inline handlers whose identity changes every render and the effect then re-arms on each keystroke; keep the current callback in a ref. **Scrolling must never edit a value** — `NumberInputGuard` from `@hms/ui` is mounted once per app and covers every `input[type=number]` including raw ones, so never copy an `onWheel` into a form. **A grid holding free text sets `[&>*]:min-w-0`**, or one long line pushes the track past the viewport and scrolls the body sideways.
- **Access refusals (binding — ADR-126):** a refusal names **which** of the two problems it is. Every page guard checks the module before the permission, in the order the server enforces: a module the hospital does not have is its _subscription_ and no administrator can grant past it (its own headline, no role list); a permission the role lacks is a question the administrator can answer today, so the screen states the permission **in words and as a key** and **which of this hospital's roles hold it** — read from that tenant's own `role_permissions`, never from `SYSTEM_ROLES`, so a custom or renamed role appears without anyone hard-coding a role name. `GET /api/v1/rbac/access?permission=…` is the one place that answers it. **`org_admin` is derived, not listed** (ADR-125, ADR-126): every permission except `OPERATOR_ONLY_PERMISSIONS` and `CLINICIAN_ONLY_PERMISSIONS`, so a key added later reaches the administrator by default and withholding one is the deliberate act. A permission is still not access — `requireModule()` runs first, so the administrator's reach is the intersection with what the hospital owns.
- **Missing values (binding — ADR-123):** a missing value **states which kind of missing it is** — never a bare `-` or `—`. Render it with `EmptyValue` / `ValueOrEmpty` from `@hms/ui`, or write it with `emptyLabel()` / `valueLabel()` where a plain string is needed (a DataTable `accessor`, a print document, an export, an accessible name). The reason is chosen at the call site — `unassigned`, `unspecified`, `notRecorded`, `notConfigured`, `notApplicable`, `none`, `notAvailable` — because only the call site knows which is true. The accessor carries the same words as the cell, so the column's filter and search can find those rows. **Investigate before labelling:** a column empty on every row is a data or query problem, and changing the placeholder instead of fixing the join, the mapper or the dataset is the failure this rule exists to prevent. A dash survives only as typography (the `–` in a reference range).
- **Action column (binding — ADR-039):** every table with row-level operations builds its Action column from `@hms/ui` — `actionsColumn()` + `TableActions` holding at most three inline actions (`ViewAction` / `EditAction` / `DeleteAction` / `ToggleAction`, or `TableAction` for a context-specific one) with `MoreActions` for the overflow. The components own icons, sizing, states, tooltips, accessible names, confirmation, and permission gating; a page supplies intent only. An action the user is not permitted is not rendered, and nothing destructive happens without the shared confirmation.
- **Branding (binding — ADR-040):** branding comes from the theme, never from a component. Only `--hms-brand` is ever set — hover, pressed, subtle, and the focus ring derive from it — and an app consuming `@hms/ui` maps those tokens onto its own scope once in its global stylesheet (marketing points `--hms-*` at `--mk-*`). No colour literal in a component, and every interactive state is verified branded in Light + Dark under a non-default accent.
- **App identity (binding — ADR-040, ADR-061):** every frontend states its identity through Next's App Router file/metadata conventions, never a hand-placed default asset. The browser-tab icon is `app/icon.svg` carrying the Nirogix mark (same geometry as `BrandMark`, literal colours because a favicon is outside the token scope) — **one mark for all five apps**; the `<title>` is per app in its `metadata`. In-app logos come from `BrandMark` (or a tenant's uploaded logo, ADR-040), never a per-app copy. Open Graph belongs only to the indexable surface (`marketing`); the four `noindex` apps carry no social image by design. **No `create-next-app` scaffolding** (`favicon.ico`, `next.svg`, `vercel.svg`, …) ever ships — it is deleted in the scaffolding change.
- **Marketing claims (binding — ADR-038):** the marketing site never advertises, implies, or depicts a capability that is not in approved scope, and never presents planned work as available. Every claim traces to the PRD / architecture / development plan / a defined phase / shipped code; module and integration status lives in `marketing/lib/availability.ts` and moves to `built` in the same change that ships the feature. Imagery is not decoration — no image without a stated communication benefit, no stock or generic healthcare photography, nothing implying an unsupported capability.
- **Database seeding (binding — ADR-058, ADR-122):** one seeder per environment — **development / staging / production** — and each **refuses to run anywhere else**. `NODE_ENV` must match the seeder's declared environment, and the guard additionally inspects `DATABASE_URL`, because the connection string is what actually decides which database gets written. Development seeds realistic **synthetic** data; staging seeds a **deterministic** production-shaped dataset for QA and E2E; production seeds **bootstrap configuration only** (permissions, system roles, a first administrator where required) behind an explicit confirmation variable. **Never** a hospital, patient, appointment or demo doctor in production, and **never real patient information** in any environment. Seeders are idempotent, print their target before writing, and hold no secrets. **Idempotent means converging on _present_, never on the dataset's values (ADR-122):** a seeder creates what is missing and never updates, resets or deletes a record that exists, because a value edited by hand on a shared environment belongs to whoever edited it. Records are matched on a **stable key** — a code, an email, a registration number, a phone number — never a display name; an action with no record of its own (a profile, a colour, a toggle, the clinical history, a column backfill) is recorded in `seed_markers` and done once; a backfill fills a newly added column **only where it is NULL**. **Staging is seeded automatically by its deployment workflow**, right after migrations, so a new table or newly required record arrives with the deploy that ships it — adding that seed logic is part of the same change. Development is run by hand; **no workflow seeds production, and none ever passes `--reset`**.
- **Communication (binding — ADR-016, ADR-059):** one `CommunicationService` (`sendEmail`, `sendSms`, `sendOtp`, `verifyOtp`, `resendOtp`) is the only code that talks to a provider. A frontend never calls MSG91 — the path is Frontend → API → CommunicationService → provider — and auth keys, template ids, sender ids and domain credentials are server-side only, from configuration, named as placeholders in `.env.example`. Never ask anyone to paste a secret into chat or source. Send the transactional messages the workflow requires and nothing else.
- **Row actions (binding — ADR-039, ADR-060):** every table is reviewed for the actions its workflow needs, chosen by role, permission, record state and business rule — not every action on every table. **A record that can be displayed incorrectly must have a permitted, safe way to be corrected.** Destructive actions confirm through the shared `ConfirmDialog`; clinical and administrative records prefer soft delete/deactivation. The button is never the boundary — the backend re-checks on every call — and important changes are audited with who/what/when/which record.
- **Before manual QA (binding):** run the **full** automated suite end to end — unit, component, API and E2E — fix every failure at the root, regression-test, re-run the full suite, and report total/passed/failed/skipped/blocked. A known failure is documented in `BACKLOG.md` or it blocks the handover to testing staff.
- **Testing (binding):** every feature ships as _implement → automated tests → manual cases in `testcases.md` → verify → complete_. Automated coverage at the level the change deserves (unit / component / API / e2e for critical workflows); a feature is not complete while a known test fails unless the acceptance is written in `BACKLOG.md`. Manual cases and automated tests are both required — neither substitutes for the other.
- **Mobile navigation (binding — ADR-033):** below the breakpoint both apps present an app shell — a fixed bottom bar with ≤5 primary destinations (permission-filtered in the Portal) plus a top-right hamburger opening the shared slide-out drawer (scroll-locked, focus-trapped, Esc/backdrop/navigation closes it). Desktop keeps its own navigation; the bar never renders there. Built from `BottomNav` / `NavDrawer` in `@hms/ui`.
- **Specializations (binding — ADR-034):** the marketing specialty experience is one reusable system (`lib/specialties.ts` + `components/specialties/`), not a page design per specialty. A dedicated `/specialties/[slug]` page exists only where there is genuinely differentiated content; everything else stays on the index. Always framed as "configured differently", never "we have a module for your specialty".
- **Language:** natural, professional English. Never hyphenate words that are not a real compound (_Hospital Management System_, not _Hospital-Management-System_); legitimate compounds (`multi-tenant`, `check-in`, `follow-up`, `India-resident`), URLs, slugs and identifiers keep their hyphens.
- **Dates & times (binding — ADR-030, ADR-046):** every user-facing date is `DD/MM/YYYY`, every time `hh:mm AM/PM`, and together `DD/MM/YYYY, hh:mm AM/PM` — formatted only through `@hms/utils` and rendered through `DateDisplay` / `TimeDisplay` / `DateTimeDisplay` in `@hms/ui`. Transport stays ISO-8601. No `toLocaleDateString()`, no per-component formatting, no date library. Chart axes are the only abbreviated form, and they use `formatMonthLabel` / `formatDayLabel` from the same place.
- **Date & time entry (binding — ADR-048):** every date or time field is `DateField` / `TimeField` / `DateTimeField` from `@hms/ui` — shadcn's Base UI date picker promoted into the kit and restyled onto the tokens. Never a native `<input type="date">`, `type="time"` or `type="datetime-local"`: they render in the browser's locale. Display in `DD/MM/YYYY` and `hh:mm AM/PM`, value in ISO.
- **Printing (binding — ADR-047):** print prints the _document_, never the application. A printable document is its own route under `app/(print)/` with no shell, built from the `@hms/ui` document kit (`PrintDocument` + sections/tables/totals/signatures/notes), carrying the tenant's own branding (platform default when unconfigured), the same permission as the screen, and the same RLS-scoped data. Never `window.print()` on an app page.
- **Public endpoints (binding — ADR-056):** the product has **one** unauthenticated write path (patient self-registration) and must not casually gain a second. Any endpoint reachable without a session resolves the tenant **server-side from an opaque token in the path** — never from a body, header, query parameter or subdomain — never writes to a clinical table, returns the **same** status and message for unknown / retired / disabled so it cannot enumerate tenants, is rate-limited at the sign-in tier, and is audited against the tenant with no actor. A public submission creates a record for a human to review; a patient, order or invoice is created only by an authenticated, permitted user.
- **API feedback (binding — ADR-026, ADR-057):** every state-changing or failing API call raises a notification through the **one** shared `@hms/ui` toast, driven from the shared API client — never per-page toast code, never a silent failure. Show the backend's own `message` when it provides one; generic copy only as a fallback. Never render a stack trace, backend internal, or PHI.
- **Notifications (binding — ADR-057):** the toast system is **React Toastify**, wrapped by `@hms/ui`'s `toast.success | error | warning | info | loading`. `react-toastify` is imported **only inside `@hms/ui`** (the adapter `src/toast.tsx` and the viewport `src/components/Toaster.tsx`); no page-specific toast implementation and no second toast library without an ADR. Toasts appear **top-right**, below the app bar, on every app and breakpoint, and take their colour only from the `--hms-*` tokens — so they follow Light/Dark and the active tenant's branding automatically. Never pass a colour to a toast. Status is never signalled by colour alone: every variant carries an icon _and_ a word. A page that already handles a failure inline opts out with `feedback: false` rather than raising a second toast for the same event.
- **SEO/AEO/GEO (binding — ADR-027):** all product SEO lives in `marketing/` — unique per-page title/description, canonical, one `<h1>`, semantic HTML, OG/social metadata, honest JSON-LD, sitemap + robots, descriptive URLs, keywords mapped to matching page intent (never stuffed). `hms_frontend/` is `noindex, nofollow` end to end; no patient/tenant/staff data in metadata, URLs, OG images, or sitemaps.
- **Frontend performance:** `next/image` (correct `sizes`, `priority` only for the real LCP image), `next/font`, `next/script` for third-party, the Next Metadata API, `next/dynamic` for heavy non-critical UI; budgets LCP ≤2.5s / INP ≤200ms / CLS ≤0.1. Audit every new dependency; no second UI library. Never send PHI or tenant-identifying data to analytics.
- **Frontend delivery workflow:** Requirements → UX → SEO (where applicable) → Accessibility → Next.js optimization → API feedback → Performance → Code cleanup. All of it is Definition of Done.
- **Frontend behaviour (binding — `resources/DESIGN.md` §9):** routes open scrolled to top; smooth scrolling via Lenis (shared `SmoothScroll`); overlays lock the background with `useScrollLock` + `data-lenis-prevent`; use the shared `BackToTop`; the marketing navbar includes About + Contact; marketing (`--mk-*`) and Portal (`--hms-*`) branding are **independent** token scopes.
- **Clean code (binding):** **if it is not used, it does not stay** — delete orphaned files, imports, exports, components, CSS, tokens, assets, empty directories, and any dependency nothing imports, in the _same_ change that orphans them. Replacing something is _migrate → verify → delete_, never two systems side by side. Regenerable scaffolding goes too; git history is the archive. Grep before deleting, typecheck + build after — that is the proof it was dead. This is a Definition-of-Done gate, not a later chore.
- **Providers:** external SDKs only behind `SmsService`/`EmailService`/`FileStorageService`.
- **Secrets:** never committed; `.env.example` documents required keys per app.
- **Environment files (binding):** **all six apps** — `hms_backend`, `marketing`, `hms_frontend`, `patient`, `admin`, `aiportal` — each keep their `.env.example` (committed) and their `.env` (gitignored) **in lockstep: the same keys, in the same order, no exceptions.** A key added to, renamed in, or removed from an `.env.example` is added to, renamed in, or removed from **that same app's local `.env` in the same change** — never "later", never "when someone next copies the file". The change is not done while the two files disagree, and this applies to every one of the six even when only one app's variable moved. Every key in `.env.example` is **live and uncommented**: an unconfigured or secret one ships as `KEY=` with an empty value, never as `# KEY=`, so copying the file yields a complete, boot-ready configuration where only the values need changing. In the local `.env` the new key gets the working local value where one exists, and an empty value otherwise — never a real secret copied into `.env.example` in the other direction. Comments are **1–2 short lines** above a key or a small group — enough to say what the key is and what a blank value falls back to; the long explanation belongs in the doc that owns the decision (`resources/`, an ADR, `SECURITY-AUDIT.md`), not in the env file. A **blank value means "not configured" and behaves exactly like an unset one** — `hms_backend/src/config/env.ts` strips blank values before Zod validation, so an empty optional URL or number can never stop the API from booting. A value containing `#` is quoted (`KEY='ChangeMe#123'`), because dotenv ends an unquoted value at the first `#`. Never a real secret, key, or password in `.env.example`; a variable no code reads is deleted from both files. **Enforced, not remembered:** `scripts/env-check.mjs` compares the key list and order of both files for all six apps and is run by the checked-in `.githooks/pre-commit` hook, so a commit that leaves them drifted is rejected. The hook is enabled by pointing git at `.githooks/`, which `scripts/setup-hooks.mjs` does from the root `prepare` script on every `npm install` (and never fails the install if git is unavailable). It never reads or prints a value — a `.env` holds real credentials — and an app whose local `.env` does not exist yet is reported and skipped, never failed. Run it yourself any time:

  ```bash
  npm run env:check
  ```

## Marketing Product Capability Documentation Rule (binding)

`resources/marketing-product-capability-reference.html` is the **single source of truth for marketing-facing product capabilities**.

Whenever any code, feature, permission, role, module, workflow, integration, UI capability, security capability, branding capability, or roadmap item changes, review whether the marketing capability reference needs updating. **If the change affects a documented capability, update the HTML document in the same development task** — never as a later chore.

- No feature may be marked `BUILT / AVAILABLE` unless it is actually implemented and usable. A screen that exists but is not wired, an API with no interface, or a capability behind a stub is **not** BUILT — say what is true (e.g. "API only, no Portal screen").
- `IN DEVELOPMENT`, `PLANNED`, and `FUTURE / CONSIDERATION` features must never be represented as currently available product functionality.
- Marketing copy must never claim functionality that cannot be traced to the approved product documentation or to implemented product behaviour.
- The capability reference must stay synchronized with the current implementation and the approved roadmap, and must stay consistent with `marketing/lib/availability.ts` + `marketing/lib/site.ts` (ADR-038), `resources/phases.md`, `BACKLOG.md` and `SECURITY-AUDIT.md`.
- Any material update also bumps the document **version**, the **last updated** date (`DD/MM/YYYY`), and appends a **change history** row.

**Golden rule.** If the product cannot currently do it, marketing must not sell it as if it can. If development changes what the product can do, the capability document changes in the same development task.
